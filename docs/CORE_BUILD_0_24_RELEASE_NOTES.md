## Task — CombatRoom Enemy Retaliation

**Date:** 2026-09-04 to 2026-09-06
**Build:** Core Build 0.24
**Status:** Implemented and verified. One additional fix was made mid-implementation, with explicit user sign-off, beyond what the approved plan specified (see "A finding during implementation" below). The load-bearing Wave 4 pocket-pull check was initially run against a substituted, weaker pocket and had to be re-run against the actual worst-case pocket after review caught the substitution (see "Wave 4" item 5) — that re-run is what the numbers below reflect. Working-tree only — nothing committed.

### Summary

CombatRoom's enemy retaliation had never worked: no code path in any of the four combat zones (Blackwire Sewers, Static Yard, Cinderworks, Saltmere Docks) ever assigned a real player to `enemy.targetPlayerSessionId`, so every enemy sat in `"idle"` forever and players took zero risk fighting there. This build ports `TownRoom.applyEnemyAggroDamage`'s proximity acquisition, leash/return-to-spawn, and telegraph/windup/landing state machine into `CombatRoom.ts`, scoped to normal hits only (heavy attacks are a named, queued follow-up, per the approved plan's Question 1). Multi-enemy aggro — each enemy independently targeting the nearest alive player — is in scope and falls out of the ported acquisition loop for free.

The zone-gating gap (no combat zone has a level/gear requirement) was explicitly accepted as-is for this build, per the plan's Question 4, contingent on Wave 4's load-bearing live check confirming the multi-enemy pocket-pull risk is genuinely reactable, not just bounded on paper. **That check passes against the actual worst-case pocket (Static Yard's wretch-north, ~4.35-4.84 real observed DPS, ~9.3s real TTK)** — see "Wave 4" item 5 below for the full numbers and why the margin is real but tighter than an earlier, substituted-pocket pass suggested — so no simultaneous-attacker-cap fallback was needed.

### What changed

- **`apps/server/src/realtime/rooms/CombatRoom.ts`** — `applyCombatEnemyAggroDamage` rewritten to port `TownRoom.applyEnemyAggroDamage`'s real logic: proximity-based target acquisition (nearest alive player, per enemy, independently), leash/aggro-range re-validation, return-to-spawn walking via the already-shared `moveEnemyTowardPoint`/`resetEnemyCombatState`/`ENEMY_RETURN_ARRIVAL_DISTANCE`/`ENEMY_RETURN_REACQUIRE_BUFFER` helpers (now imported for the first time), idle wandering via the already-shared `applyWanderMovement`, and the telegraph → windup → landing sequence. `attackKind` stays hardcoded `"normal"` — the four `heavyAttack*` content fields and `nextHeavyAttackAtMs` are read by nobody in this build, exactly per the Question 1 cut.
- **`damage_applied` is now sent from CombatRoom's landing branch** (previously only `enemy_attack_resolved` was sent) — this drives the client's existing player-hit-flash/floating-damage-number/camera-shake-on-downed feedback (`WorldSessionScene.onDamageApplied`), which was already wired for TownRoom but had nothing to trigger it in CombatRoom before this build.
- **A latent unit-conversion bug in the pre-existing (dead) code was fixed as part of the port**: the old `applyCombatEnemyAggroDamage` passed enemy `moveSpeed` through `toWorldUnits` (a ×24 tile-to-pixel conversion meant for `aggroRange`/`leashRange` only), which would have made enemies move roughly 24x too fast the moment they ever got a real target. Since targeting never worked, this was never observed. The ported version matches TownRoom's real formula (`moveSpeed * ENEMY_MOVEMENT_SPEED_UNITS_PER_SECOND_MULTIPLIER`, no `toWorldUnits`).
- **CombatRoom-only divergence from TownRoom, added mid-implementation (see below): enemies stop moving while a telegraph is in flight** (`attackLandingAtMs > 0`). TownRoom's identical aggro loop keeps chasing every tick regardless of windup state; this build's dodge test found that behavior makes TownRoom's own "dodge causes a miss" code path structurally unreachable for a single dodge (the chasing enemy re-closes the gap before the miss-check ever sees the player still out of range). This is a real, newly-discovered, pre-existing gap in TownRoom's shared aggro logic — not something 0.24 introduced — but it directly undermines dodge's usefulness in the room this build's whole job is to make combat real in. Fixing it only in CombatRoom (freezing movement during an active windup) was chosen over leaving it broken or fixing TownRoom too (a larger, unplanned change to a second room's shared combat logic). TownRoom's own dodge behavior is unchanged and still carries the same gap — flagged here explicitly, not silently left for someone to rediscover.

### A finding during implementation: dodge did not actually work as assumed

While writing the plan's committed "dodge-causes-a-miss" vitest test, tracing the ported (and TownRoom-identical) code showed that a single dodge does not reliably avoid a telegraphed hit: the chasing enemy re-closes the gap between the dodge distance (60 world units) and attack range (44 world units) well within the 300ms windup, at typical enemy move speeds (~9-14 world units per 50ms tick). The "miss" branch's own distance re-check can only ever be reached once the enemy has already re-entered range, so it can never actually fire from a single one-shot dodge — this held in both a Blackwire Sewers vitest run and independent arithmetic, and applies identically to TownRoom's own shipped code (TownRoom has no test covering this either).

This was surfaced to the user mid-session with two options: accept it as a pre-existing, out-of-scope TownRoom gap and adjust the test/live-check expectations to match reality, or fix it within 0.24's scope. **The user chose to fix it.** The fix — freeze the enemy's chase movement while a telegraph is already in flight — is scoped to `CombatRoom.ts` only (see "What changed" above); it is a real, named, CombatRoom/TownRoom behavioral divergence, not silently introduced.

### Non-goals held

- Heavy attacks (`attackKind: "heavy"`, the `heavyAttack*` content fields) — cut per Question 1, queued as an immediate named follow-up build ("CombatRoom Heavy Attack Parity").
- Zone-level/gear gating — explicitly accepted as-is per Question 4, queued as a named follow-up ("Zone-Level/Gear Gating").
- No enemy content values (damage, HP, `heavyAttackDamage`) or the `mitigateIncomingDamage` formula were changed.
- No shared-helper-module extraction — CombatRoom's port is a direct, room-local copy of the acquisition/telegraph/landing logic, matching 0.12's dodge/flask precedent. This does mean CombatRoom and TownRoom each now carry their own full copy of this state machine (already-diverging further, given the windup-freeze fix above) — a real, named duplication cost, not a surprise.
- No simultaneous-attacker cap — the pre-committed fallback was not needed; see the live-check outcome below.

### Verification — vitest (`apps/server/test/`)

New tests, all in `apps/server/test/combat/`:

- **`enemyAggroAcquisition.test.ts`** — the core regression: an idle enemy, with no manually-preset target, acquires a co-located player by proximity, telegraphs (`enemy_attack_telegraph` received, `attackKind: "normal"`), and lands a real, armor-mitigated hit. This is the first CombatRoom test that doesn't fake acquisition.
- **`heavyAnchorNormalOnlyGuard.test.ts`** — Saltmere Docks' Drowned Hauler (heavy-attack-capable: `heavyAttackDamage: 7 > damage: 4`), isolated from every other enemy, lands only its normal damage across several real attack cycles — a regression guard so a future change can't silently reintroduce the heavy branch unnoticed.
- **`enemyLeashReturn.test.ts`** — a mid-chase enemy whose target moves out of aggro range is dropped, switches to `"returning"`, walks back to its real spawn point, and re-idles.
- **`dodgeAvoidsRetaliation.test.ts`** — dodging mid-windup (after the CombatRoom-only freeze fix above) resolves the telegraph as a server-authoritative `"miss"`, with zero HP lost. First test of its kind in either room.
- **`flaskAfterRetaliationDamage.test.ts`** — a real, mitigated retaliation hit (via the real landing code path) followed by a real flask heal, proving the interaction, not just each piece in isolation.
- **`realRetaliationDeathReturnsToTown.test.ts`** — a real enemy hit that brings HP to exactly 0 downs the player, and `request_respawn` still redirects to Nightmarket (Core 0.14's handoff), proving death-to-Nightmarket is reachable through the real damage path for the first time (the existing `deathReturnsToTown.test.ts` manually pokes `hp = 0` and was kept as-is, not replaced).

**Fixed as a consequence of the port**: `test/combat/incomingDamageMitigation.test.ts` (0.11) manually preset `targetPlayerSessionId`/`attackLandingAtMs` without co-locating the enemy's `spawnX`/`spawnY` — safe under the old (broken) code, which had no leash logic to trip, but the newly-real leash re-check cleared the target before the landing tick ran. Fixed by co-locating enemy and player at the enemy's own real spawn point, mirroring `test/town/incomingDamageMitigation.test.ts`'s existing fixture shape exactly.

**New shared test helper**: `apps/server/test/support/isolateSingleEnemy.ts` — moves every enemy except the one under test far away and clears its targeting state. Needed because multi-enemy aggro is now real: a test that co-locates a player with one enemy's spawn point can otherwise also pull a second enemy from the same tight spawn pocket, which is correct, intended behavior but breaks single-enemy test isolation.

**Regression-check discipline**: the full CombatRoom.ts port was temporarily reverted (`git stash`) and the 6 new test files re-run. 4 of them (`enemyAggroAcquisition`, `enemyLeashReturn`, `heavyAnchorNormalOnlyGuard`, `dodgeAvoidsRetaliation`) failed exactly as expected — they depend on the newly-ported acquisition/leash/telegraph machinery. The other 2 (`flaskAfterRetaliationDamage`, `realRetaliationDeathReturnsToTown`) passed even against the old code, because — like the pre-existing 0.11 mitigation tests — they use the established "preset the target and landing time directly" shortcut to exercise the always-correct landing math, not acquisition itself (acquisition is proven separately). The port was restored; full suite re-confirmed green.

**Final state**: 33 test files, 52 tests, all passing. `pnpm -r typecheck` clean across all 5 typechecked workspace packages.

### Wave 4: the live Playwright check

First time CombatRoom damage-taken and death were observed in a real browser. Findings, in order:

1. **Basic single-enemy retaliation (Blackwire Sewers)**: a fresh character walked up to an idle Trashboar Runt with no prior interaction. Confirmed live: real proximity acquisition (`state=chasing`, `target=<real session id>` visible in the debug overlay), a real telegraph, and `"Enemy attack hits for 2."` / `"-2 HP (37 remaining)"` — exactly `trashboar_runt`'s content `damage: 2`, unmitigated (armor 0), matching the plan's numbers precisely. HP orb and UI feedback updated correctly.
2. **Dodge**: with the CombatRoom-only windup-freeze fix in place, dodging mid-telegraph produced a live `"Enemy attack missed."` with `"Dodge is on cooldown."` shown on the immediately-following (correctly rejected) second attempt, and zero HP lost. Confirms the fix works end-to-end, not just in the unit test.
3. **Flask mid-fight (Blackwire Sewers)**: took a real hit (45→41 HP), pressed the flask hotkey, HP rose to 43 (a partial increase, not the full +25, because ongoing combat — a second real hit — landed inside the same observation window; consistent with, not contradicting, the flask mechanism working, and independently confirmed exactly by the deterministic `flaskAfterRetaliationDamage.test.ts`).
4. **Heavy-anchor normal-only (Saltmere Docks, Drowned Hauler)**: engaging the Hauler alongside nearby common enemies (brine crawlers/tide stalkers — multi-enemy aggro is real and was visibly active here too) produced a noisy but fully consistent damage sequence (deltas of 2, 4, 6, 14 — every one decomposable into 2s and 4s only, the zone's only two enemy damage values; the Hauler's own 4-damage hit was directly observed via `"Enemy attack hits for 4."`-shaped feedback and matching debug-panel HP deltas). No 7-damage hit was ever observed, corroborating `heavyAnchorNormalOnlyGuard.test.ts`'s deterministic guarantee live.
5. **The load-bearing check — a full 3-enemy common-tier pocket pull on a fresh, unarmored character, against the actual named worst-case pocket.**

   A first pass used Saltmere Docks' `crawler_pocket_north` (3× Brine Crawler, 6.00 theoretical combined DPS) as a stand-in, after client-side gate-click navigation to Cinderworks/Static Yard proved too unreliable to pin down live (see "Environment notes"). That pass observed only ~3.33 dps actual — roughly half the pocket's own theoretical ceiling — which is a materially weaker result than Q2's 6.67 DPS / ~6.75s TTK for Static Yard's wretch-north or Cinderworks' hound-north, and does not confirm the same ratio holds for the actual worst-case pockets. **This was re-run directly against Static Yard's `wretch_pocket_north`** (3× Static Wretch, the real 6.67-DPS pocket Q2 identified), using a direct database write to place a fresh, unarmored character exactly at the pocket's center (`225, 180`) before ever calling `request_move` — `currentZoneId`/`lastLocationZoneId`/`lastLocationX`/`lastLocationY`/`currentHp` set directly on the `Character` row via `docker exec ... psql`, then the client's existing "Enter World" flow (which already reads the character's persisted zone/position and restores it verbatim in `buildCombatPlayerPresence` when it matches the zone being joined) placed the character there with no gate-click navigation at all. The server-side aggro/damage logic doesn't know or care how the character arrived.

   **Real observed result**: all three Static Wretches acquired the player within about a second of spawning (three simultaneous `"INCOMING"` telegraph banners, visually stacked, all three enemies `state=chasing` on the same target — screenshotted). HP then fell in clean, near-perfectly-synchronized **−6 volleys roughly every 1.2-1.3 seconds** (three simultaneous 2-damage hits landing together), a much spikier and more front-loaded pattern than crawler-north's staggered −2/−4 trickle: 45→33→27→21→15→9→3→0. **Total time from spawn to 0 HP: ~9.3 seconds. Real observed DPS: ~4.35-4.84** (measured both from the clean post-entry polling segment and from the full spawn-to-death span) — **65-73% of the 6.67 theoretical ceiling**, closer to theoretical than crawler-north's ~50-56% but still short of it; real TTK came in about 38% longer than Q2's 6.75s theoretical estimate, i.e. measurably safer than the paper worst case, though by a smaller margin than the substituted pocket implied.

   **Verdict: the criterion still passes, but by a real, smaller margin than the crawler-north data suggested, not "the same result."** The triple-stacked `"INCOMING"` telegraph the instant all three enemies acquire is an extremely loud, unambiguous danger signal — closer to "surrounded, get out now" than a subtle trickle — so a first-time player has every reason to notice within the first volley (~1.2s, 87% HP remaining) and every visual cue to keep noticing each subsequent one. Even a player slow enough to react only after 3 volleys (~3.75-5s elapsed, 47-60% HP remaining) retains a real, if tighter, margin to retreat, dodge, or flask before the ~9.3s death mark. A player who stays fully passive for 5+ volleys (6+ seconds, the scenario this automated test necessarily ran) is the same explicitly-named "worst-case upper bound, not the expected experience" the plan's Question 2 already called out, not the standard being tested. **No simultaneous-attacker cap was implemented** — the pre-committed fallback was reserved for this check failing, and on the real pocket, with the real numbers, it did not.
6. **Death observed live**: both in the Static Yard wretch-north run above (the character was allowed to reach 0 HP rather than stopped early) and in an earlier Saltmere Docks pass, HP reached 0 under real multi-enemy pressure; this is the same real-damage-to-zero path `realRetaliationDeathReturnsToTown.test.ts` proves deterministically.

**Environment notes** (not gameplay findings):
- Headless Chromium intermittently threw a client-side `Cannot read properties of null (reading 'drawImage')` error during the town→combat room-switch handoff, leaving the old scene visually frozen despite the server-side WebSocket handoff completing correctly underneath (confirmed via direct network/WebSocket instrumentation: the old room's socket closed, the new room's socket opened, exactly as expected). Switching to non-headless (real GPU) Chromium made this reproducible far less often (roughly 1 in 4 attempts still hit it) — this reads as a software-WebGL/headless-rendering artifact specific to this automation environment, not a real client bug, and is unrelated to Core 0.24's server-side changes.
- Pixel-accurate gate-click navigation to a specific distant zone/pocket proved unreliable and slow to calibrate blind (screen-to-world mapping isn't a fixed transform — it drifts with camera-follow state, which itself isn't deterministic session-to-session). The direct-DB-fixture approach used for the wretch-north re-run (set `currentZoneId`/`lastLocationX`/`Y` on the `Character` row, then let the existing "Enter World" flow's own persisted-position-restore logic do the rest) is the more reliable pattern for placing a test character at an exact position in a specific zone going forward, and is recommended over pixel-hunting for anyone repeating this kind of check.
